{#- Top-N table shell with server-side paging, sorting, search, filter chips, column chooser and export (plan 14.5). What `data_table(id, columns, rows, src=..., total=..., page=..., page_size=..., sort=..., order=...)` renders one self-contained table block. Every control re-asks the server through htmx: the server answers with the same macro for the new page, and htmx swaps the whole block (`outerHTML` on `#id`). The same macro serves the first page render and every fragment, so the two can never drift. Pages build the context from an admin API table answer with `roxy.admin.pages.kit.table_view` and call `data_table(**table)`. Why Dashboard tables can have millions of rows (endpoint records, clients); only the server can sort and page them honestly (v1 sorted rendered rows in the browser, so "top 25" meant "top 25 of what was sent"). Paging sizes 10, 25, 50, 100 and 250 are kept from v1, and the choices a person makes (rows per page, hidden columns) are remembered per table in this browser by static/js/tables.js. How State lives in one form (`#id-state`): q, filters, the page-level parameters in `keep` (the time range), and hidden page, page_size, sort and order inputs. The names are the admin API's own (DESIGN.md 13: `page`, `page_size`, `sort`, `order`, `q`), so the same query string pages the fragment and exports through the API. The search box asks after a short pause; selects ask on change; sort headers, the pager and the rows-per-page select set the hidden inputs and submit the form (tables.js), so there is exactly one request shape: `GET src?q=&page=&page_size=&sort=&order=&=&=`. Row cells carry `data-label` so phones can show each row as a card with the key columns (`key_col`) and open the rest in the drawer (plan 14.8). The export menu links to the API route (`export_url`) with `format=csv|json` and the current search and filters; static/js/exports.js downloads it, says "try again in a few seconds" on a 429 and warns when the file was cut (`Roxy-Export-Truncated`).
